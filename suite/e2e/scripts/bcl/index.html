blockchain-link request baseline

loading…
Counts how many requests Trezor Suite sends to blockchain backends, per coin, so we can measure whether an optimization reduces them. Lower is better. Each coin is measured in two phases: discovery (enabling the coin & scanning its accounts) and idle (the app sitting still afterwards). Every number is captured from a real desktop app run in CI.
What do these numbers mean? (glossary)
logical request
One high-level call Suite makes to the blockchain-link layer (e.g. “get account info”, “estimate fee”). This is what the app asks for, before any per-backend fan-out.
backend (wire) request
One actual RPC / WebSocket message that leaves the app to the coin’s backend server. Device-bridge traffic and the firmware/config CDN are excluded — only real blockchain backend calls are counted.
amplification (amp ×)
backend ÷ logical. How many real backend calls each logical request explodes into. ~1× = thin (blockbook: BTC-like). High = fat fan-out where one logical call becomes many backend calls (Solana, EVM: token accounts, per-tx fetches, staking).
discovery phase
The request burst when the coin is enabled and Suite scans its accounts to find balances and history. Bounded in the log by markers.
idle phase
The app sitting idle after discovery. Measures the steady-state background load: periodic account sync, re-sync on every new block, keep-alive pings, fiat polling.
idle /min
Idle backend requests per minute — a rate, so runs with different idle lengths compare fairly.
before → after (diff)
Pick two runs to compare. A number in red means more requests than the “before” run (worse); green means fewer (better).
