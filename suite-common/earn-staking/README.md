# @suite-common/earn-staking

Staking logic shared by the desktop, web and mobile apps: the product repository and, later, the staking state, engine and view-model hooks. Apps and shared packages import this package and `@suite-common/earn-staking-common`, which holds the contracts.

The products live in `@suite-common/earn-staking-products`, which this package must not import; `forbiddenDeps.config.ts` enforces it. The application composition roots register the products and expose them to this package as the injected product repository, under `services.staking`.

Both apps register the state as `state.earn.staking`, under the `earn` key that yield and lending will join later. Shared code never names the root: selectors and thunks are typed on `StakingRootState`.

Product info is server data, so it lives in the app's shared query client under `commonQueryKeys.stakingProductInfo`, fetched through the product adapters by `refreshStakingProductInfoThunk`; the redux state holds the platform, the descriptors and the positions only.

Staking operations run as sessions, one per account, product and operation, keyed by `getStakingSessionKey`. A session holds the plan and one status-tagged entry per step: `pending`, `composed`, `signing`, `signed`, `broadcasting`, `awaiting`, `done` or `failed`. A recoverable error keeps the step where the next thunk can retry it and sits on the step as a kind and code; `failed` is an on-chain outcome. The review modal and screens read the step that is signing, signed or broadcasting through `selectStakingReview`, which is derived from the sessions, so nothing can go stale. Sessions are not persisted.

The engine thunks in `src/engine` drive a session step by step through the product adapter: plan, compose, sign, broadcast, cancel a step and discard a session. Every compose and signing call is an attempt the step records, and a result that arrives after a newer attempt started, or after the session was planned again, is dropped; a plan result only replaces a session older than the plan request. Signing runs inside the injected `StakingDeviceAccess`, `services.staking.deviceAccess`: a pass-through on desktop and web, where Connect already serialises device calls, and the prioritised device mutex on mobile. It is also the one place that cancels a device call, and only for the attempt whose call is on the device, so a queued attempt never aborts another call and an older attempt that finishes late never hides a newer one. An adapter reports a device or app cancellation and the validity timeout as `StakingAdapterError` codes from `STAKING_SIGNING_ERROR_CODES`; any other Connect failure keeps its Connect code, or becomes `signing-failed` when it has none, never its message. A failed broadcast keeps the step signed with the same signature and refreshes the account, because the push may have reached the network anyway: a retry sends the same bytes, and only expiry or a cancel returns the step to `composed`.

Confirmation does not depend on a mounted page. `prepareStakingMiddleware` settles an awaiting step from the `addTransaction` that carries one of its transactions mined. A step keeps every txid a replacement gives it, marked as a cancel or not, and settles on whichever one mines: the original or a bump confirms it, a transaction the chain rejected fails it, and a mined cancel fails it as `replaced`. `trackStakingStepConfirmationThunk`, started by the broadcast thunk, seeds that check from the stored transactions and then polls the account at the network's block interval for up to fifteen minutes; afterwards the apps' own syncs keep feeding the middleware.

`toPrecomposedLevels` turns a composed step into the precomposed levels the existing fee pickers accept.

`@suite-common/earn-staking/mocks` holds test factories.
