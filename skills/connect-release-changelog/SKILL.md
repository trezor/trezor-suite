# Connect release changelog

A stable Connect release bumps `@trezor/connect` and every published package it depends on. [release-connect-bump-versions.yml](../../.github/workflows/release-connect-bump-versions.yml) runs [connect-bump-versions.ts](../../scripts/ci/connect-bump-versions.ts), which opens the `npm-release: @trezor/connect <version>` pull request from the `bump-versions/connect-<version>` branch.

- Each package gets a commit `npm-release: @trezor/<package> <version>`. It adds a raw `# <version>` section to the package's `CHANGELOG.md`, one `- <subject> (<hash>)` line per commit that touched the package since its previous release.
- `packages/connect/CHANGELOG.md` only gets new version tables. Its `# <version>` section is written by hand.

Check out the release pull request (`gh pr checkout <number>`), rewrite every raw section into release notes, then write the Connect section and push one commit to the release branch. Changelogs ship inside the npm packages, so a mistake stays in the published version.

## Readers

- `packages/connect/CHANGELOG.md`: integrators of any Connect package. Methods, params, behavior, coins and firmware, deprecations, and what they have to do.
- `connect-web`, `connect-webextension`, `connect-mobile`: integrators of that entry point. Only changes to the package's own code and behavior, the rest belongs in the Connect changelog. Keep the pointer to the Connect changelog at the top of the file.
- Every other package: developers who import it directly. What its entry point exports, how it behaves, and what it installs or loads at runtime.

## Classify each commit

The raw section is the complete input. Do not add commits that are not in it.

Read the commit message and the diff inside the package. When that diff does not explain the impact, read the rest of the commit. For regenerated protobuf definitions read the `.ts` files, not `*_pb.js`.

```bash
git show --stat <hash> -- <package dir>
git show <hash> -- <package dir>
```

Decide from the diff. The commit type is not a reliable signal:

- A `chore` can be breaking or visible: a removed or moved export, a removed param, a major or native dependency bump, regenerated protobuf definitions, bundled firmware or coin data.
- A `feat` or `fix` under another scope, such as `feat(suite): ...`, can add API to this package or only touch it in passing.
- A `refactor` is internal unless it changes exported names or types.

A change is breaking when code that worked with the previous version can fail or silently do something else: a removed, renamed or moved export, param or field, a type made stricter (an optional field made required), a changed default, or a renamed param the method now ignores. Say what a call with the old form does now.

Leave out tests, tooling, formatting sweeps, internal refactors, README and other docs edits, release bookkeeping and commits that only edit `CHANGELOG.md`. A docs commit that states new requirements for integrators belongs in the Connect changelog, with every requirement it states. Describe only the user-facing part of a mixed commit. Merge commits that make one change into one bullet when one short sentence still covers them.

## Write

- One plain sentence per change. Start with what the reader now gets or has to do, and add the mechanism only when the reader can act on it.
- When a value, default or dependency changes, give the old and the new value. For a narrowed set of allowed values, name the removed ones. For a changed default, say what a caller who overrides it must now provide.
- Copy the hashes as the raw section writes them: `- <sentence> (<hash>, <hash>)`.
- Breaking changes first, each starting with `Breaking:`. Then deprecations, then the rest, most important first.
- Code names in backticks: exports, methods, params, settings, error codes.
- No intro paragraph, extra headings, bold labels, emoji or em dashes. Nothing the reader cannot act on.
- Do not guess. Check a condition in the code before you state it, and add no code snippet you have not type-checked. A package you tell readers to install must be on npm or released in this pull request. When the diff does not show the impact, keep the raw line and tell the person running the release.
- When nothing is left, write `- No user-facing changes.` Keep `- Version bump only.` where the script wrote it.

### Example

```markdown
# 10.0.2

- Added Arc and Arc Testnet EVM networks (6e8bf873a90)
- Bundled firmware 2.13.0 release data for T2T1, T2B1, T3B1, T3T1 and T3W1 (5173ffe463f)
- Zcash and Zcash Testnet block time changed from 150 s to 25 s for NU7 (0bc4cb34ce9)
```

### Anti-example

Raw subjects. The firmware change hides behind `chore` and the docs commit only fixes links. Write the example above instead.

```markdown
# 10.0.2

- chore(connect-common): bundle FW 2.13.0 for core (5173ffe463f)
- docs: fix more links in mds (4126a230c5a)
- feat(suite): add Arc and Arc Testnet support (6e8bf873a90)
```

## Connect changelog

After the package sections, write the `# <version>` section of `packages/connect/CHANGELOG.md` below the version tables. Write it from the curated sections of every package in the release, not only the `connect*` ones: `blockchain-link`, `transport` and the network packages change what Connect methods return.

- The Write rules apply. A `Breaking:` bullet may add one sentence with what the integrator has to do, and names the affected packages inside the sentence. Keep a patch release short. When it gets long, shorten fixes and mechanisms first, never a breaking change or a required action.
- After the breaking changes and deprecations come new methods and params, coin and firmware support, then fixes an integrator notices. Point to a package changelog instead of repeating long lists of removed names.
- Leave out internal details such as development servers, timings, data formats Connect negotiates with the firmware and the reasons behind Suite behavior. Hardening the integrator cannot observe stays out. One they can observe gets one neutral sentence without the mechanism.
- Take firmware requirements from the `min` entries in `packages/connect-core/src/data/config.ts`. A model they do not list is not gated.
- `@trezor/connect` runs the core in the integrator's Node process. `connect-web`, `connect-webextension` and `connect-mobile` run each call in Trezor Suite, so a core change reaches them with a Suite release. They re-export the types, events and constants of `@trezor/connect-common`, so a change there reaches all three with this release. Say so when the two differ. Name a Suite version only after checking it: release branches get cherry-picks under new hashes, so look for the subject in the release tag (`git log --format=%s v<version> | grep -xF '<subject>'`, `v<version>@mobile` for Suite Lite).

## Check

Cited hashes must come from the raw sections, which stay in `HEAD` until you commit. Every `not in` line is an error. Read the `left out` lines once more before you commit.

```bash
previous=<previous Connect version>
hashes() { awk '/^# /{n++} n==1' | grep -oE '\(([0-9a-f]{7,}(, )?)+\)' | grep -oE '[0-9a-f]{7,}' | cut -c1-10 | sort -u; }
for f in $(git diff HEAD --name-only -- '*CHANGELOG.md' ':!packages/connect/CHANGELOG.md'); do
    comm -23 <(hashes < "$f") <(git show HEAD:"$f" | hashes) | sed "s|^|$f: not in the raw section: |"
    comm -13 <(hashes < "$f") <(git show HEAD:"$f" | hashes) | sed "s|^|$f: left out: |"
done
release=$(git log -1 --format=%H --grep="^npm-release: @trezor/connect $previous\$")
comm -23 <(hashes < packages/connect/CHANGELOG.md) <(git log --format=%H "$release"..HEAD | cut -c1-10 | sort -u) | sed 's|^|packages/connect/CHANGELOG.md: not in the release: |'
yarn prettier --check $(git diff HEAD --name-only -- '*CHANGELOG.md')
```

Commit as `docs(connect): curate the <version> changelogs` and push to the release branch.
